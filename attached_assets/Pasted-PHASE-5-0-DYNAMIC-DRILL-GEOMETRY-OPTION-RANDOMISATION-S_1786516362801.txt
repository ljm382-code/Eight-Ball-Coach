PHASE 5.0 — DYNAMIC DRILL GEOMETRY, OPTION RANDOMISATION & SCENARIO INTEGRITY

The current 8-Ball Coach build is structurally stable, but several live drills are still not realistic enough for a coaching/training application.

This patch must improve the ACTUAL TRAINING QUALITY.

Do NOT redesign the app.

Do NOT change:

* adaptive rating mathematics
* confidence mathematics
* match intelligence
* root-cause analysis
* Mixed Training weighting
* persistence
* navigation
* Sage–Teal theme
* canonical English ball colours
* shared PoolTable renderer
* English table orientation
* existing rules legality

This phase fixes only:

1. Unrealistic shot orientation.
2. Repetitive drill geometry.
3. Duplicate or incomplete decision options.
4. Correct answers appearing in predictable positions.
5. Diagram/text inconsistencies.
6. Inconsistent table markings.
7. Lack of dynamic scenario variety.

⸻

1. CORE TRAINING PRINCIPLE

8-Ball Coach is a TRAINING APPLICATION, not a game.

Each drill must teach or assess a genuine cue-sports skill.

A drill must not merely:

* look different,
* pass validation,
* move a ball a few pixels,
* or present four generic choices.

The table position, instructions, options, and coaching feedback must describe the SAME physical situation.

⸻

2. TABLE AXIS TERMINOLOGY

Standardise these concepts:

type TableAxis =
  | "long"
  | "cross"
  | "diagonal"
  | "mixed";

Meaning:

long

Shot primarily travels along the long dimension of the table.

cross

Shot primarily travels across the shorter table width.

diagonal

Shot traverses a significant diagonal.

mixed

Multi-shot route uses more than one meaningful axis.

Add optional authored metadata:

shotAxis?: TableAxis;

This is coaching metadata only.

It must not affect rules logic.

⸻

3. LONG POT MUST ACTUALLY BE LONG

The current live:

Long Pot — Full Length

is visually running across the short dimension of the table.

This is incorrect.

Rewrite its authored diagram.

The shot must run approximately along the LONG axis.

Using the existing convention:

LEFT = rack end
RIGHT = baulk end

Place the cue ball toward one short-end region and the object ball toward the opposite end.

Example normalized geometry:

cueBall: {
  id: "CB",
  group: "cue",
  x: 82,
  y: 54
}
objectBall: {
  id: "Y1",
  group: "yellow",
  x: 18,
  y: 54
}
targetPocket: "topLeft" // or another authored end pocket

Do not copy these exact coordinates blindly if the pocket line is not geometrically correct.

The resulting shot must visibly travel most of the table length.

⸻

4. LONG-POT ACCEPTANCE RULE

For any drill whose name or objective contains:

* long pot
* full length
* full-table pot

validate that:

abs(cue.x - object.x)

represents at least approximately:

55% of playable table length

or another documented threshold appropriate to current coordinates.

It must NOT qualify as a long pot merely because the cue/object distance is large across the short axis.

⸻

5. SCREW / DRAW DRILLS

The current Screw Shot also uses a largely short-axis setup.

Redesign the base screw drill so it predominantly uses the LONG axis.

Preferred structure:

RIGHT side:
white cue ball

mid-table:
yellow object ball

LEFT/end pocket:
target pocket

After contact:

cue-ball draw route travels BACK toward the right/starting side into a visible target zone.

The diagram must clearly distinguish:

OBJECT BALL PATH:
object → target pocket

from:

CUE BALL PATH:
contact point → draw-back target zone

⸻

6. SCREW SHOT REQUIRED VISUALS

The Screw Shot must show:

* white cue ball
* yellow/red object ball
* intended pocket
* cue → object aim segment
* object → pocket potting segment
* separate backward cue-ball route
* target zone behind the cue-ball/object contact direction

Do not represent screw only with a target box.

The cue-ball backward route must be visible.

⸻

7. SHOT-GEOMETRY MIX

Most drills should exploit the TABLE LENGTH because this is often where meaningful English-pool position and potting practice occurs.

However, the library must not become repetitive.

Target approximate authored distribution across execution drills:

LONG AXIS       ~50–60%
DIAGONAL        ~20–25%
CROSS TABLE     ~15–20%
MIXED ROUTE     remainder

This is a content-quality target, not an adaptive weighting rule.

Do NOT force these exact percentages if the drill concept requires otherwise.

⸻

8. DISTINCT DRILL GEOMETRY

Within one drill family, do not repeatedly use the same central vertical setup.

Example potting family should include genuinely different geometry:

pot1

Straight middle-pocket pot.

pot2

Long-axis full-length pot.

pot3

Diagonal cut.

pot4

Thin cut or rail-influenced pot.

The diagrams should look obviously different at a glance.

9. POSITIONAL FAMILY VARIETY

Positional drills should include:

* long-axis follow
* long-axis screw/draw
* cross-table position
* diagonal natural-angle position
* one-cushion route
* two-cushion route where difficulty warrants it

Do not repeatedly place cue and object balls on the centre vertical line.

* long lag

* two-cushion speed

1 → 3 → 2 → Black

generateBallOrderPermutations(

16. DECISION UI DOES NOT NEED TO SHOW ALL SIX EVERY TIME

For mobile usability, do NOT automatically show six huge answer cards unless intentionally desired.

Instead:

* derive the five other distinct permutations,
* select 3 distinct distractor routes,
* present 4 total choices.

But:

NO duplicates.

The four shown routes must be unique.

18. CORRECT OPTION MUST NOT ALWAYS BE FIRST

This is critical.

The current app shows a pattern where the strongest/correct option repeatedly appears first.

That teaches the UI rather than the skill.

Remove this pattern entirely.

⸻

19. OPTION RANDOMISATION

Create a pure helper such as:

function shuffleDecisionOptions<T>(
  options: T[],
  seed: string
): T[]

Use a deterministic seeded shuffle.

The correct answer identity remains attached to the OPTION itself.

Do not encode correctness by array index.

Bad:

correctIndex = 0;

Good:

{
  id: "routeC",
  tier: "optimal"
}

Then shuffle the array.

⸻

20. SEED BEHAVIOUR

Use a stable but varying presentation seed based on something such as:

profile.id
drill.id
session.id
attemptNumber

or equivalent existing identifiers.

Goal:

the same player should not always see the optimal answer in the same position.

Do not use uncontrolled Math.random() if it makes tests nondeterministic.

⸻

21. CORRECT-ANSWER POSITION DISTRIBUTION

Across the decision-drill library and test seeds:

2
3
4

Add an automated distribution test.

For a large enough deterministic seed sample, each position should occur more than zero times.

22. DO NOT SHUFFLE AFTER PLAYER SELECTS

Option order must remain stable for the duration of a drill attempt.

Compute the shuffled options once for that presented drill.

Do not reshuffle during React re-renders.

Use:

useMemo(...)

or equivalent stable session construction.

A long-axis drill should have meaningful:

and sufficiently large deltaX.

Do not require mathematically perfect angles.
