PHASE 4.8 — COMPLETE TRAINING-DIAGRAM CONSISTENCY ENFORCEMENT

The current 8-Ball Coach app still has inconsistent training diagrams.

Some drills now have correct:
- English table geometry
- baulk line / D
- target zones
- aim lines
- target-pocket indicators

while other drills still display generic tables with missing geometry.

THIS MUST END.

8-Ball Coach is a TRAINING APPLICATION.

Every drill shown to a player must have a diagram that accurately represents the exact setup, objective, shot geometry and success criteria of that drill.

Do NOT add new product features.
Do NOT redesign navigation or theme.
Do NOT change adaptive rating logic.
Do NOT change confidence logic.
Do NOT change match intelligence.
Do NOT change rules penalties.
Do NOT change Mixed Training weighting.
Do NOT change persistence.

This phase is ONLY about making ALL drill diagrams complete, authored, consistent and impossible to fall back to generic misleading geometry.

==================================================
1. ROOT CAUSE TO ELIMINATE
==================================================

The current App.tsx execution path contains logic equivalent to:

if (drill.diagram)
  render <PoolTable diagram={drill.diagram} />
else
  render <ExecDrillDiagram />

and decision drills similarly fall back to:

<DecisionDrillDiagram />

This is no longer acceptable for training content.

Generic visual fallbacks are the primary reason some tables have complete geometry while others do not.

==================================================
2. NEW NON-NEGOTIABLE RULE
==================================================

ANY drill that can be:

- assessmentEligible
- assigned by generateSession()
- shown in Drill Library as playable
- used in a clearance
- used in a decision exercise

MUST have a complete authored TrainingDiagram.

No authored diagram = drill cannot be presented to the player.

==================================================
3. REMOVE GENERIC TRAINING FALLBACKS
==================================================

For real training/assessment content:

REMOVE the use of:

ExecDrillDiagram
DecisionDrillDiagram

as player-facing fallback renderers.

They may remain only for:
- internal component preview
- developer story/demo
- non-playable placeholder

They must NEVER appear in an assessment or generated training session.

==================================================
4. FAIL LOUDLY IN DEVELOPMENT
==================================================

If a playable drill has no valid diagram:

DO NOT silently display a generic table.

In development:

throw/log a clear error such as:

"Playable drill pot2 has no complete TrainingDiagram"

In production:

exclude that drill from assignment and surface a safe unavailable-state if somehow reached.

Never display fake geometry.

==================================================
5. CREATE ONE GEOMETRY COMPLETENESS CONTRACT
==================================================

Create a pure helper:

validatePlayableDrillGeometry(drill)

Return:

{
  valid: boolean,
  errors: string[]
}

This must validate the ACTUAL requirements of the drill.

Not merely:

diagram exists

but:

diagram contains everything its training content requires.

==================================================
8. POT DRILL GEOMETRY STANDARD
==================================================

Every potting drill must show:

- exactly one white cue ball
- exact object ball(s)
- intended pocket
- object-ball potting line
- cue-to-object aim segment when instructional
- table positions corresponding to stated difficulty

Examples:

STRAIGHT POT
cue → object → pocket collinear

ANGLED POT
cue-object line differs from object-pocket line
visible cut angle

LONG POT
object and cue separated by realistic table distance

THIN CUT
geometry visibly produces a thin cut

Do not reuse straight-pot geometry for angled/thin drills.

==================================================
9. SPEED DRILL GEOMETRY STANDARD
==================================================

Every speed/touch drill must show:

- white cue
- object ball if applicable
- intended pocket/contact
- clearly visible target zone
- cue-ball end zone
- route length appropriate to drill difficulty

Examples:

Stop-Ball Speed Gate:
small stop zone around contact position

Two-Cushion Speed Control:
visible two-cushion cue route
target zone after second cushion

Soft Touch Safety Roll:
short-distance end zone
safety/object-ball relationship

Precision Lag:
clear finishing zone near cushion

==================================================
10. POSITIONAL DRILL GEOMETRY STANDARD
==================================================

Every positional drill must show:

- cue ball
- current object ball
- next ball
- intended pocket
- visible cue-ball target zone
- cue-ball route

For:

Simple Follow
→ forward route

Screw Round the Angle
→ draw/screw route backward from contact

Side-Spin Route
→ cushion interaction visible

Congested Cluster Route
→ actual obstacle balls forming the congestion

The geometry must visibly distinguish these drills.

==================================================
11. CUE-BALL CONTROL STANDARD
==================================================

Basic Stun:

- object
- intended pocket
- cue stopping/sideways travel result
- visible target marker

Screw Shot:

- object
- backward target zone
- draw route

Swerve:

- curved/schematic route around blocker
- target object

Do NOT show identical diagrams for stun and screw.

==================================================
12. PROBLEM-BALL EXECUTION STANDARD

13. BREAK DRILL STANDARD
==================================================

All break diagrams must show:

- vertical baulk line

Then vary drill intent:

control-oriented cue placement

Break for a Pot:
authored break line / target area relevant to pot attempt

Restricted Break:
ruleset-specific legal cue placement clearly shown

Do not use a 2-ball diagram for ANY break drill.

==================================================
14. BLACK-BALL DRILL STANDARD
